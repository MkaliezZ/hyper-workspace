# 企业 AI IM：可行性与开源选型

> 历史研究材料：当前有效定义与选型已固定在 [AI-IM 开发基线 v1.0](./AI-IM基线/README.md)。本文的 Nextcloud 整套 AI 路线、LangGraph 默认执行层及 Context Chat 默认知识库建议已被后续决定替代；保留正文作为选型过程记录。

核查日期：2026-10-29（Asia/Shanghai）。

本次完成官方文档、公开仓库 README、部分 LICENSE 和功能分级核查；没有部署候选产品，没有进行模型连通性、中文任务成功率、并发、客户端推送或安全实测。下文“已实现”指官方资料明确列出，不代表已在本公司环境验证。维护活动、许可证与功能均须在实施时按选定版本再次锁定。

## 1. 结论与建议

技术上可行。可复用成熟 IM、办公协作和 Agent 模块，主要自研工作是身份与权限映射、群聊 Agent 交互、业务工具适配、任务执行可靠性和统一界面。

本次没有找到可直接认定满足全部要求的成品：完全开源、公司内自部署、接近飞书/企微/钉钉的基础办公能力、自带可配置模型 Key，并且所有纳入范围的业务操作都能由 AI 完成。

已有接近的方案，不能简单说市场上没有实现：

- **Nextcloud Hub + Talk + Assistant + Context Agent**：最接近现成办公协作底座，已有跨办公模块的 AI 执行动作。
- **Matrix + MindRoom**：最接近多人、多 Agent 同处群聊的交互方式，已有模型配置、工具、记忆和权限机制。
- **Block Buzz**：已有强 AI 协作与工作区操作能力，但移动端、推送、工作流审批仍有明显未完成项。

**当前首选：以 Nextcloud 做内部试点，围绕 Talk 增加 Agent 执行服务。** 原因是企业实际要用的文件、日历、任务、协作与通话可以尽量复用一套系统。先验证其中文体验、移动通知、群聊执行链路和并发限制；如果聊天与 Agent 体验不达标，再改选 Matrix + MindRoom。两条路线择一作为主聊天系统，不同时运行两套 IM。

如果“界面操作要高度贴近国内 IM”是硬要求，唐僧叨叨可进入候选，但客户端授权与通信版本兼容性尚未核清，暂不直接定为正式底座。

## 2. 把需求变成可验收范围

“基础功能贴近飞书”建议先定义为：组织账号与通讯录、单聊/群聊、文字/图片/文件/语音、消息搜索与离线恢复、通知、日历与任务、共享文件/知识库、音视频会议、管理后台。

审批、考勤、报销、复杂在线表格、客户联系等需逐项纳入，不能把 IM 已有误认为这些业务已齐全。考勤还涉及位置、设备等真实输入，AI 可以填报、解释、查询和发起流程，不能生成虚构考勤事实。

“所有功能 AI 驱动”的工程定义：每个纳入范围的业务动作，均有可鉴权、可校验、可追踪的工具/API；AI 和按钮调用同一业务服务。AI 能读、创建、修改、执行和回读结果。需要确认的业务动作仍可由 AI 发起并呈现确认界面。

关键约束：

1. 每个工具继承真实发起人的可见范围和操作权限；不能让所有员工通过一个管理员机器人操作。
2. AI 不可见的部门文档、私聊、文件，不得进入检索结果、摘要、记忆或任务上下文。
3. API Key 配置至少有 provider、base_url、model、secret；可选公司统一 Key、个人 Key、部门额度与模型分配。
4. 模型能聊天不等于能可靠调用工具。逐模型测试工具调用、结构化输出、中文理解、长上下文和多步骤执行。
5. 把任务“已发起”“后台成功”“收件人收到”“业务处理完成”分别记录，成功回执以实际对象与状态为准。

## 3. 整体方案候选比较

| 候选 | 官方资料已明确的能力 | 与需求的差距 | 当前判断 |
| --- | --- | --- | --- |
| [Nextcloud](https://nextcloud.com/) + [Talk](https://github.com/nextcloud/spreed) + [Context Agent](https://github.com/nextcloud/context_agent) | 文件、聊天、会议和办公应用；Agent 工具覆盖消息、文件、日历、任务、团队、看板等；模型连接可配 Key | 国内式 OA、完整组织树和统一群聊 Agent 执行体验仍需补；Context Agent 文档明确当前不能横向扩展 | 首选试点底座，不能据文档直接保证容量 |
| [MindRoom](https://github.com/mindroom-ai/mindroom) + Matrix | Agent 是 Matrix 用户；多模型、多 Agent、工具/MCP、记忆、管理界面、工具审批与沙箱 | 不包含完整国内 OA；中文端体验、企业账号接入、长期稳定性与端到端权限要试点 | AI 群聊路线首选候选 |
| [Buzz](https://github.com/block/buzz) | 群组、线程、私信、搜索、画布、审计、CLI、ACP Agent、事件触发工作流 | README 将移动端、工作流审批门、部分语音事件列为建设中，推送列为待实现；偏开发团队 | 可研究或局部试用，暂不作为全员 IM 首选 |
| [唐僧叨叨](https://github.com/TangSengDaoDao/TangSengDaoDaoServer) + [WuKongIM](https://github.com/WuKongIM/WuKongIM) | 中文多端 IM 应用及消息通信底座 | 非完整办公套件；全业务 AI 工具需要开发；Web/PC 仓库独立 LICENSE 本次未找到；WuKongIM 当前主线 v3 为 beta | 中文体验二开候选，授权与版本核清后再决定 |
| [OpenIM](https://github.com/openimsdk/open-im-server) | IM Server/SDK、群组、消息接口和回调 | 官方明确主要是面向开发者的 IM 解决方案；不能当成直接可用的完整办公产品；客户端仓库许可证需分别检查 | 深度自研 IM 时的备选 |
| [Mattermost + Agents](https://docs.mattermost.com/administration-guide/configure/agents-admin-guide) | 成熟团队聊天、多模型连接、内置与外部工具集成 | 免费级与 Enterprise 功能不同；状态变更 MCP、远程 MCP、多模型等关键能力有授权分级；插件 enterprise 目录另有许可证 | 不把官方完整 AI 能力计入纯开源方案 |
| [Rocket.Chat](https://docs.rocket.chat/v1/docs/mcp-server) | 企业聊天与官方 AI/MCP 方向 | 官方 MCP 要求 AI add-on、用户权限与管理员开关，且当前标为 Alpha | 不把官方 AI add-on 当免费开源功能 |
| [Cheers](https://github.com/haowei2000/Cheers) | 人与外部 ACP Agent 同群、文件上下文、自部署；AGPL-3.0-or-later | 原生移动客户端未上架，社区和发布成熟度仍需独立评估；并非完整办公套件 | 补充观察候选 |

## 4. Nextcloud 到底已有多少 AI 执行能力

[官方 Context Agent 工具清单](https://docs.nextcloud.com/server/stable/admin_manual/ai/app_context_agent.html)已经列出：日历安排、任务创建/更新/完成、团队成员管理、文件操作、看板分派、Talk 消息操作等。这证明其已有实际操作接口，仍须按公司任务逐条验收。

例如，“创建一个团队”和“创建一个私密聊天群并按部门批量加人”是不同操作。不能用工具清单中的前者推断后者已完整支持。

[模型连接组件](https://github.com/nextcloud/integration_openai)支持多个 OpenAI-compatible 服务，管理员能设置服务 Key，个人也可设置自己的凭据。DeepSeek、通义等接入要以具体 endpoint 与模型能力实测，不根据协议名称直接承诺全部兼容。

[官方 Talk AI Bot](https://github.com/nextcloud/talk_bot_ai)已经支持在群聊里 @assistant 问答，但其 README 只明确保证问答，不能认定已将 Context Agent 的所有执行工具完整接入群聊。因此“群聊里一句话跨模块办事”是本方案明确要验证和补齐的集成工作。

Context Agent 同时提供有鉴权的 MCP 接口。可以通过新的执行服务复用这些工具，并在工具调用之前完成身份映射、权限验证和必要确认；不把普通机器人收到的消息自动解释为管理员授权。

## 5. 按模块选型

推荐路线 A：办公协作优先。

| 模块 | 首选 | 采用方式与边界 |
| --- | --- | --- |
| 账号、聊天、文件、日历、任务 | Nextcloud 对应应用 + Talk | 复用现成服务与客户端；确认组织结构需求能否直接表达，缺口自研 |
| 模型 Key 配置 | integration_openai | 第一阶段直接使用原有配置；公司 Key 与个人 Key 的使用策略需统一 |
| 群聊 Agent 执行服务 | Python + LangGraph 开源库 | 新开发 Talk 消息入口、身份映射、任务状态和执行回执；不依赖商业托管产品 |
| 办公工具 | Context Agent MCP + 官方业务 API | 复用现有工具，缺失动作新增适配器；工具调用按发起人身份执行 |
| 知识检索 | 先用 Context Chat；定制需求再用 PostgreSQL + pgvector | 不并行堆两套检索系统；权限过滤必须覆盖索引、检索、引用、记忆与撤权 |
| 模型网关 | LiteLLM 非 enterprise 部分，按需引入 | 需要跨系统模型路由、配额时再加入；不要假定企业 SSO、SCIM、审计等都在开源范围 |
| 审批流程 | 简单待办确认先自行实现；复杂流程采用 Flowable 开源引擎 | 引擎不等于完整 OA，表单、流程规则、审批 UI、通知和审计需实现 |
| 音视频 | 优先沿用 Talk | 需部署及验证 TURN/通话后端、移动网络、录制和转写；独立 IM 路线可选 LiveKit |
| 可观测与任务记录 | 独立任务/工具调用记录 + 数据库 | 记录调用人、目标对象、模型、消耗、确认、失败和实际结果；不依赖网关商业审计功能 |

推荐路线 A 的业务流：

```text
员工在 Talk 私聊或群聊中发出指令
  → 消息适配器验证签名/来源，识别真实员工和会话
  → Agent 解析任务，必要时询问缺失参数
  → 模型通过 integration_openai 或可选模型网关调用
  → 执行服务按员工身份检查工具和资源权限
  → 需要确认时在当前会话呈现预览与确认
  → Context Agent MCP / 业务 API / 审批引擎
  → 回读对象与状态，向当前会话返回链接与执行结果
```

建议采用共同的动作契约：`action_id`、请求人、会话、工具名、参数、权限判断、确认状态、幂等键、执行状态、对象 ID、实际结果。这里是自研内部设计建议，不是现有项目内置 schema。

推荐路线 B：AI 群聊优先。

采用 Matrix 自托管消息服务 + MindRoom + 相容的客户端；模型和 Agent 配置先复用 MindRoom；办公系统通过 MCP/API 接入。选定 homeserver、客户端及其许可证后再固定 BOM。MindRoom 的工具可用性、访问权限、工具审批与业务系统权限分别配置，不能相互替代。

路线 B 不再额外部署 LangGraph 来重复 MindRoom 的主要运行时职责。只有明确的业务流程缺口才新增专用服务。保留 Nextcloud 文件/日历等作为业务系统时，不再把 Talk 作为第二个主 IM。

## 6. 全功能 AI 化的验收方法

每个上线功能建立“按钮动作—工具/API—权限—确认—结果证据”映射。一个功能只有做到 AI 可操作并回读实际结果，才标为支持；仅能回答使用方法的不算完成。

第一阶段至少验收以下场景：

1. 配置一个真实模型 Key 和自定义 endpoint，实际完成问答与工具调用；更换模型后重测。
2. 两个真实测试账号互发消息；测试离线恢复、跨端同步和手机通知。
3. 群聊总结生成带原消息引用的纪要，来源只限授权历史。
4. 从讨论生成任务，分配负责人和截止日期，回读任务对象。
5. 根据参与人空闲时间安排日历事件，向正确会话发通知。
6. 检索公司制度并返回来源，跨部门账号不能看到无权限内容。
7. 生成一份业务文档、存入指定目录、以正确权限分享。
8. 创建私密项目群并加入指定人员；若现成工具不覆盖，新增接口后验收。
9. 发起一条简单请假或报销流程，正确提交给审批人；AI 不替代有权审批人的决定。
10. 重复事件、模型超时、执行后断网和进程重启不会重复建群、发消息或提交审批；失败有明确回执。
11. 同一群内两个员工并发调用，私有资料、凭据和审批不会串用。
12. 撤销文件权限或移出部门后，搜索、记忆和进行中的任务均遵守新权限。

质量建议：权限隔离与重复执行防护是上线硬门槛。常见中文任务的成功率、完成耗时和每任务消耗应实测并商定门槛；本次不编造成功率。

“所有功能”的分母以已确定的第一版功能清单为准，任何未支持动作都要显式列为缺口，不用“接了 MCP”替代覆盖率验证。

## 7. 工作量和运行成本

以下仅为工程粗估，假设 20–100 名内部员工、主要使用现成客户端和云模型 API、有 2–3 名熟悉相关栈的工程人员参与，不含完整历史迁移和重写全部移动客户端。

| 阶段 | 交付 | 粗估日历时间 |
| --- | --- | --- |
| 技术验证 | 一套可登录环境、一种模型、三个真实业务动作、双账号隔离、手机通知初验 | 1–2 周 |
| 内部 MVP | 群聊 Agent、文件/日历/任务、基本模型管理、确认与回执、首批场景验收 | 从启动累计约 4–8 周 |
| 稳定内部版本 | 权限回归、恢复与备份、升级演练、并发/成本测试、客户端适配、重点审批 | 从启动累计约 8–16 周 |

这些是容量和需求尚未确认前的规划假设，不是交付承诺。高度贴近国内产品的自研界面、复杂审批和全端定制会显著增加工作量。

成本应分为服务器/存储/带宽与备份、模型调用、语音转写与向量化、持续维护。开源软件可以减少授权支出，但不会免除这些成本。外部模型 API 路线不要求自建推理 GPU；资料会按请求内容进入所选模型服务，自部署 IM 不等于模型处理也留在内网。

模型费用按实测账本计算：输入 token × 对应单价 + 输出 token × 对应单价 + embedding/转写等费用，需考虑工具循环、失败重试和历史压缩。没有模型、业务量与数据规模前，不给伪精确月费。

## 8. 许可证与版本核查记录

这是一份组件选择记录，不替代上线前的完整依赖清单审查。

- Nextcloud Context Agent：[LICENSE](https://github.com/nextcloud/context_agent/blob/main/LICENSE)为 AGPLv3；其他应用与客户端分别核查。
- MindRoom：[README 许可证段落](https://github.com/mindroom-ai/mindroom#license)区分主体 Apache-2.0 与 saas-platform 的 BSL-1.1；不能称全仓都是 Apache-2.0。
- Buzz：[仓库](https://github.com/block/buzz)显示 Apache-2.0；README 的成熟度表是本次筛选的重要依据。
- 唐僧叨叨：[官方指南](https://tsdaodao.com/guide/)声明 Apache-v2.0；但 [Web/PC 仓库](https://github.com/TangSengDaoDao/TangSengDaoDaoWeb)本次未找到根目录 LICENSE，也未在 README 找到独立授权段落，故客户端授权标为未核清。不能用服务端许可证代替每个客户端的许可证。
- WuKongIM：[当前 README](https://github.com/WuKongIM/WuKongIM)标注 v3 beta，默认 Demo 模型是模拟模型。必须固定与唐僧叨叨相容的版本，不能把最新主线拼接视为已验证兼容。
- OpenIM：[服务端](https://github.com/openimsdk/open-im-server)为 Apache-2.0；不推断客户端、SDK 和 Demo 全部相同。
- LangGraph：[开源库 LICENSE](https://github.com/langchain-ai/langgraph/blob/main/LICENSE)为 MIT；采用开源库不等于需要其商业平台。
- LiteLLM：[LICENSE](https://github.com/BerriAI/litellm/blob/main/LICENSE)区分 enterprise 目录与其他 MIT 代码。
- Flowable：[开源引擎 README](https://github.com/flowable/flowable-engine)声明 Apache-2.0；不把商业低代码套件计入开源交付。
- LiveKit：[服务端 LICENSE](https://github.com/livekit/livekit/blob/master/LICENSE)为 Apache-2.0；托管云、录制、转写等能力分别确认部署和成本。
- pgvector：[LICENSE](https://github.com/pgvector/pgvector/blob/master/LICENSE)采用 PostgreSQL 风格宽松许可。

## 9. 本次决定和待验证项

已完成：候选初筛、官方功能核查、关键版本/授权限制核查、模块选型建议、集成架构和验收方案。

建议执行顺序：先用 Nextcloud 路线完成小范围技术验证；优先验证最容易影响全局选型的中文工具调用、群聊到执行链路、用户权限、移动通知与 Context Agent 并发能力。通过后进入 MVP；不通过则对照 Matrix + MindRoom 路线试验，再锁定主架构。

未完成且不能视为既成事实：安装部署、模型 API 连通、任何业务端到端执行、压力测试、公司实际权限验证、现有飞书/企微/钉钉数据迁移。

实施前还需明确员工规模、首批业务清单、是否必须原生移动端、现有账号体系、部署位置和模型服务。当前评估可在这些信息缺失时成立，容量和工期则仍属假设。
