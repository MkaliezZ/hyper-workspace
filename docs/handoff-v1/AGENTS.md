# 企业 AI IM：Agent 开发规则

适用范围：本交接包及采用本包作为开发依据的代码仓库。若在其他代码目录工作，须在其根部接入本文件的规则入口。阅读后再规划或修改代码。

## 1. 规则优先级

遵守平台/系统及开发环境的有效指令。其下以当前用户明确指令为先；用户后续明确修改某项基线时，更新对应版本与影响记录。已有明确授权持续有效，不为相同动作重复询问。

本包中：本文件约束工作方式；AI-IM基线/ 中的 v1.0 文件共同定义产品和技术；开发交接状态.md 描述打包时状态；历史可行性报告仅供参考。正文与 JSON 共同组成基线，发生矛盾时记录具体冲突并修订，不能静默选一份解释。

阅读顺序见根 README。无需原聊天即可接手。

## 2. 固定产品方向

开发公司内部使用、可长期维护的 AI IM 产品。复用开源模块，提供自有产品界面与业务核心。所有纳入范围的业务功能需有获准的 AI 操作入口，并与人工界面使用相同业务服务。

审美层是公司的工作判断：目的、人机关系、价值取舍、主动尺度、成果质量、表达体验。不得将其缩减为配色或系统提示词。P01–P08、C00–C07、A01–A10 的定义保留在原基线中。

界面应体现聊天、项目上下文、任务/成果与执行状态，支持修改和接管。美术细节可以在该方向内设计；当前没有固定品牌色、字体、Logo 或像素级稿件。

## 3. 固定技术与职责

- 前端 React + TypeScript；业务后端 TypeScript + NestJS。
- 首版模块化单体、独立执行 Worker、Docker Compose。
- 默认 DSH；Hermes 是必须实现和验证的兼容执行器。
- PostgreSQL 管理业务、关系和资产目录；pgvector 管理可重建语义索引；pg-boss 管理后台任务。
- Nextcloud Talk、Files/WebDAV、Calendar/CalDAV 分别经 Provider 接口接入。
- 自有 PolicyService、Identity/Authorization、Project/Task/Artifact、Asset/Knowledge、RunService、ToolGateway、ModelProvider 与 EngineAdapter。

Routine 实现细节、目录、库版本和兼容版本组合可按现有授权自主选择，并留下锁定清单与理由。默认执行器、主要框架、数据所有权、跨引擎语义或首版核心依赖的改变属于基线变更，需有用户的相应授权；已有授权足够时继续执行并记录，无须再问。

## 4. 模块边界

产品会话、业务待办 Task、执行 Run、消息 Message、决定 Decision、成果 ArtifactVersion 分别建模并关联。

两个执行器都经同一版本化 EngineAdapter；业务与前端不得直接依赖引擎内部事件或私有数据库。共同能力统一验收，引擎扩展显式声明。新任务可路由切换；运行中任务保留原执行器或先停止并对账后在安全业务边界重启，不承诺私有检查点热迁移或零适配维护成本。

企业知识、关系、个人/项目记忆、成果及回执通过产品服务持久化。执行器本地记忆、会话文件和缓存不能成为唯一企业资产来源。向量索引不能替代当前业务状态或原始文件。

原始消息、文件和日历以各自源系统为权威，产品副本和目录维护源 ID、版本、权限和删除关系。集成通过公开 API，不直接改 Nextcloud 数据表。

## 5. 可追溯性与真实执行

新增或修改功能时引用对应 Policy、Capability、Asset 与验收场景编号，并写明输入、允许动作、结果、完成标准、失败和恢复方式。新增数据来源还要有明确的对象/字段/时间范围、凭据引用、权限、更新/撤权/删除规则。

权限、授权、预算与工具范围由服务端强制检查。模型得到的来源内容没有修改规则的权限。员工身份来自后端验证，不能由模型参数自行声明。

实际动作经 ToolGateway 执行并回读；幂等与对账在业务层落实。取消不等于回滚；结果不明进入 recovery_required。有效授权范围内的低风险动作无需逐步重复确认。

每个 Run 记录有效规则版本、主体、模型配置引用、工具范围与回执。对外返回产品事件和成果引用，不以一段生成文本代替执行成功。

## 6. 首版范围与暂缓项

优先实施基线中的项目讨论转纪要与待办、项目周报、反馈修改、静默跟进；首阶段建立两执行器共同契约，并按 E01–E10 收集证据。

图片、音视频、复杂表格、在线协作编辑、复杂审批、原生客户端按基线分阶段补齐。暂缓项不等于产品长期永久排除。

LangGraph、MindRoom、Context Chat、Nextcloud Assistant/Context Agent、LiteLLM、独立向量库/图数据库、Flowable、独立音视频服务、Kubernetes 不进入首版核心，除非有记录且获准的具体缺口变更。

## 7. 开发证据与状态报告

先检查实际仓库、现有代码和适用指令，保留用户已有修改。交接包只有规则，不能把其中的状态当作代码仓库当前状态。

Mock、fixture、契约测试、真实引擎连接、实际模型调用、业务端到端验收、生产部署分别标记。没有真实 Key 或环境时可以推进不依赖它们的工作，真实链路保持未验证并明确缺项。

禁止把来源绑定为空改写成“已接入公司数据”，或把未运行 E01–E10 改写成通过。公司规模、真实群组/文件目录、具体模型和版本都不能编造。用户未指定的设计细节在边界内自主处理。

软件版本和官方能力在实施时重新核对，锁定兼容版本、源码/发行包和镜像摘要；不依赖 main/master/upcoming 的变化冒充稳定组合。

本包不携带生产 Key 或企业资料，不提供对外发布、向第三方发消息或导入生产资料的独立授权。实际行动范围由当前用户任务和已有授权确定。

## 8. 交付与变更

每个开发里程碑交付：代码、启动说明、配置示例（无秘密）、迁移与回退说明、Policy/Capability/Asset 映射、实际测试结果与仍未验证项。需要的测试以行为、权限、执行恢复和跨引擎契约为主。

基线变更用变更记录模板.md 记录原因、用户授权依据、受影响编号、替代方案、接口/数据影响、测试与回退，并同步正文和 JSON。不能先换栈再把文档改成已获准。

原始交接快照保留可校验；代码仓库中的新规则版本与实施状态另行更新。
