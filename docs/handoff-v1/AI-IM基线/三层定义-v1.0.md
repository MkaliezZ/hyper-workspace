# 审美层、功能层、资产层：固定定义 v1.0

固定日期：2026-10-29。配套编号与结构见 product-baseline.v1.json。

## 1. 三层定义

| 层 | 固定定义 | 必须交付的定义 |
| --- | --- | --- |
| 审美层 / Policy Pack | 公司的工作审美：对工作目的、协作关系、价值排序、主动程度、成果质量和表达体验的一组可版本化判断规则 | 立场、适用场景、取舍、行为偏好、限制、正反例、验收依据 |
| 功能层 / Capability | 将工作审美实现为可组合、可鉴权、可执行和可验收的工作能力 | 输入、依赖资产、允许动作、权限、输出、完成标准、失败与恢复行为 |
| 资产层 / Asset | 支撑工作的事实、内容、关系、方法和成果，以及它们的身份、来源、版本、权限和生命周期 | 资产类别、来源绑定、字段、关联、权威性、更新/删除、可见范围和使用规则 |

审美层属于产品与组织规则，独立于具体模型、执行器、框架和页面样式。视觉与语言风格是审美的表达部分。Policy Pack 同时表达希望系统积极实现的工作状态和必要边界。

推导路径固定为：审美主张 → 工作场景 → 系统行为 → 功能契约 → 资产契约 → 界面与实现 → 验收证据。资产可获得性和使用反馈反向约束实现；缺失数据要标注缺口，不能据审美理想虚构事实。

## 2. 工作审美的六个维度

1. 工作目的：让讨论持续转化为成果，减少信息搬运与反复协调。
2. 人机关系：人表达意图、方向与关键决定；AI 负责获准范围内的信息组织、执行、跟进和交付。
3. 价值排序：事实准确与权限边界优先；范围明确后，优先形成可用、可修改的完整交付，并约束时间与费用。
4. 主动尺度：已指派任务主动推进；普通对话保持克制；重要变化、阻塞、完成和确需人判断时通知。
5. 成果质量：输出能使用、能检查、能修改，相关事实和执行结果有依据。
6. 表达体验：成果与下一步清晰可见，详细过程按需展开，用户能调整、停止或接管。

凭据录入、身份认证等环节按相应系统机制完成；“AI 可驱动”不意味着把秘密放入模型上下文或让模型自行授予权限。

## 3. Policy Pack 固定规则

| 编号 | 主张 | 对系统的要求 | 明确不接受的表现 |
| --- | --- | --- | --- |
| P01 | 讨论沉淀为成果 | 获准的项目讨论可以转为决定、任务和成果，并保留来源关系 | 回复“已处理”，实际没有任务或成果对象 |
| P02 | 理解连续的工作上下文 | 用项目、人员、文档版本和决定关系解释“这个项目”“上次方案”；歧义影响执行时澄清 | 只凭同名、相似度或最近一条消息认定目标 |
| P03 | 主动参与有分寸 | 在授权范围内推进，按重要程度和用户偏好合并通知 | 对每条群消息插话、状态未变仍反复提醒 |
| P04 | 人保持掌控 | 作用范围可见，可纠正、取消和接管；超出已有授权的动作再取得授权 | 用普通群消息推导出管理员权力，或每个低风险步骤都要求重复确认 |
| P05 | 成果持续可修改 | 成果有稳定 ID、版本、反馈和修改入口，区分草稿、待验收与已验收 | 更新文件后丢失旧版及反馈依据 |
| P06 | 经验形成复用资产 | 将被验证的方法、模板和案例保存为可复用资产；与原始事实分开记录 | 把一次猜测自动升级为公司制度 |
| P07 | 事实与结果有依据 | 业务状态查询权威来源，引用可访问来源，未知明确标识；实际执行后回读 | 用历史摘要判定当前审批已通过，或把执行器文本当成功回执 |
| P08 | 表达清晰且节制 | 先呈现结果、状态和必要下一步；详细日志按需展开；语言适合实际工作 | 用大量技术日志掩盖用户需要的结论 |

规则适用层级：组织基线 → 工作区/项目覆盖 → 任务约束 → 个人表达偏好。有效权限取交集，范围限制优先，授权只能通过有权主体修改。偏好冲突按更具体的适用范围处理；同级冲突且影响结果时交由有权人决定，不由模型自由选择。

规则分两类实施：权限、数据范围、预算和动作许可等在业务服务中强制检查；语气、克制程度、成果质量等通过提示、界面和评估样例共同实现。把 Policy Pack 填入系统提示词只能完成其中一部分。

## 4. 功能层

功能保留六组主能力，并补充基础通信与配置能力。

| 编号 | 能力 | 首版结果 |
| --- | --- | --- |
| C00 | 基础通信与身份 | 认证、通讯录映射、单聊/群聊、消息与附件、历史同步、搜索、通知、管理；逐项提供服务/API 与适当的 AI 动作 |
| C01 | 理解工作 | 形成有目标、范围、约束、缺口和完成标准的任务说明 |
| C02 | 获取上下文 | 从获准来源取得当前事实、历史、相关资料和可追溯引用 |
| C03 | 组织协作 | 关联项目、群、人员、任务与日历，建立分工并保留关键决定 |
| C04 | 制作与修改成果 | 生成、保存、反馈、修订和查看版本，输出可使用成果 |
| C05 | 推进与验证执行 | 调用工具、维护进度、等待必要确认、恢复失败、回读与报告 |
| C06 | 沉淀经验 | 形成有来源和验证状态的方法、模板与案例，可复用和撤回 |
| C07 | 管理模型与产品配置 | 配置公司/个人模型 Key、endpoint、模型用途、额度、规则与引擎路由 |

每个具体功能规格必须声明 policy_ids、asset_ids、输入、操作、权限、输出、完成标准、失败/恢复、通知行为、AI 调用入口与人工操作入口。按钮与 AI 使用同一业务服务；不能出现仅靠 AI 文本宣称完成的旁路。

Task 是业务待办，Run 是一次 AI 执行；Message 是通信对象，Decision 是已记录的决定，ArtifactVersion 是成果版本。对象分别建模并建立关系，防止把聊天记录作为全部业务状态。

## 5. 资产层

五类资产固定为：事实资产、内容资产、关系资产、方法资产、成果资产。为接入与验收提供十种具体资产契约：

| 编号 | 类别 | 对象或数据类型 | 主要权威来源 |
| --- | --- | --- | --- |
| A01 | 事实 | 员工、组织、角色、成员关系 | 身份来源与产品授权记录 |
| A02 | 事实 | 项目、里程碑、业务待办、日历和流程状态 | 对应业务系统/产品服务 |
| A03 | 内容 | 消息、回复关系、附件引用 | 通信服务 |
| A04 | 内容 | 文本、Markdown、PDF、办公文档与表格 | 文件来源与经核验的解析结果 |
| A05 | 内容 | 图片、音频、视频、转写/OCR及时间定位 | 原件与带处理版本的派生内容 |
| A06 | 关系 | 人—项目、群—项目、文档—任务、决定—依据等 | 产品关系目录与来源映射 |
| A07 | 方法 | SOP、术语、模板、质量量规和有效案例 | 有维护人和版本的发布记录 |
| A08 | 成果 | 成果对象、版本、差异、引用和验收状态 | 产品成果目录及文件版本 |
| A09 | 成果 | 反馈、验收记录、评估结果及改进记录 | 用户反馈和真实评估记录 |
| A10 | 事实 | Run、工具调用、授权、消耗、实际回执 | 产品执行服务及下游系统 |

资产最少记录：asset_id、category、type、workspace_id、来源与源对象 ID、owner、权限引用、源版本、采集/更新时间、有效性/新鲜度、派生关系、内容位置、删除状态。索引另存 embedding 模型、维度与索引版本。

具体来源绑定还必须声明：支撑哪些规则/功能/场景，连接哪个来源，选择哪些对象/字段/时间段，认证引用是什么，如何更新、撤权和删除。现阶段实际来源绑定为空；示例不代表公司已经存在或已授权接入的数据。

数据处理链路：登记来源 → 验证读取范围 → 解析/提取 → 版本与关联 → 按需索引 → 检索时重新鉴权 → 返回来源 → 更新或撤回。向量是可重建派生索引；审批等当前业务状态直接查询权威业务系统。

原始事实、用户声明、AI 推断、建议和经人确认的方法分别标记。个人偏好、项目记忆、组织知识按各自范围存放。执行器本地记忆和会话文件只作运行状态或缓存，不成为公司唯一资产存储。

## 6. 固定的首版体验与实施顺序

首版完整产品界面由聊天区、项目上下文区、任务/成果区和执行状态组成。项目区展示目标、关键决定、任务与当前有效成果；过程日志按需查看，成果有修改入口。

第一阶段先跑通：文本/Markdown、可提取文本的 PDF、常用办公文件的受控解析、消息与项目/任务等结构化记录；无法可靠解析的内容显式报告。图片、语音、视频、复杂表格和在线协作编辑在后续阶段补齐处理与评估，资产类型已纳入范围，尚未声称已支持。

首阶段场景：项目讨论转纪要与待办、项目周报、已有成果的反馈修改、授权任务的静默跟进。每项在 DSH 与 Hermes 下使用同一业务接口、资料范围和验收标准。后续补全排期、会议及复杂审批能力。

## 7. 变更与验收

每个新增功能/来源必须引用至少一个 Policy 编号和一个场景。改变工作审美、数据类别或功能完成标准时更新三层版本；更换框架不能静默改变产品规则。

P01/P05/P07 通过真实成果、版本与回执验收；P02 通过歧义识别和来源/版本测试验收；P03/P08 通过通知轨迹、任务样例及人工质量评分验收；P04 通过身份、权限、确认和接管测试验收；P06 通过复用效果、来源、验证状态和撤回测试验收。

固定验收场景编号为 E01–E10，详见 JSON。尚无实际运行结果，不预填通过率。
