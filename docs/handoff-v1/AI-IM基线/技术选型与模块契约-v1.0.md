# 技术选型与模块契约 v1.0

固定日期：2026-10-29（Asia/Shanghai）
状态：已选定的设计路线；实现与生产验收尚未开始。
上位约束：[三层定义-v1.0.md](./三层定义-v1.0.md)。

## 1. 复核结论

三层定义适合本项目，固定为 v1.0。原有技术选型部分保留、部分替换。

关键原因：产品要求理解项目上下文、积累关系、管理可修改成果、形成跨引擎一致行为。这要求产品层掌握 Policy、业务对象、资产和任务生命周期。仅把 Agent 挂在现成 IM 上，不能自动获得这些能力。

| 技术位置 | 原建议 | 固定决定 | 三层依据 |
| --- | --- | --- | --- |
| 产品界面和核心 | 以 Nextcloud 套件作为完整产品起点 | 自有产品界面与核心，Nextcloud 经 Provider 接口提供通信/文件/日历 | P02/P05/P08；C03/C04；A06/A08 |
| 默认执行层 | LangGraph，后讨论 DSH/Hermes | DSH 默认，Hermes 为必须实现并验收的兼容执行器 | P04/P07；C05；A10 |
| 执行器切换 | 抽象为统一接口 | 固定版本化 EngineAdapter；首阶段双执行器契约测试 | 相同 Policy/Capability/Asset 语义 |
| 企业知识与记忆 | Context Chat 或执行器内置记忆 | 独立资产/知识服务，执行器通过受控工具使用 | P02/P06/P07；A01–A10 |
| 向量数据库 | PostgreSQL + pgvector | 保留，首版不另加独立向量数据库 | 内容检索与结构化权限/关系共同管理 |
| 模型 Key | Nextcloud integration_openai 配置 | 自有 ModelProvider 管理，供两个适配器解析 | C07，避免由某一应用掌握唯一配置 |
| 日历/业务待办 | Nextcloud Calendar/Tasks/Deck | 日历沿用 Calendar；项目、待办、决定和成果元数据由产品核心掌握 | C03–C05；A02/A06/A08 |
| Nextcloud AI 模块 | Assistant、Context Agent 和 Talk AI Bot | 从首版必需链路移除，必要时作为工具来源适配 | 已有执行层；避免重复的 Policy/任务/知识状态 |
| 任务调度 | 可能使用执行器 cron | 产品核心调度，pg-boss 处理后台任务；执行器不重复拥有企业日程 | P03/P07；C05；A10 |
| 其他框架 | 多个候选同时保留 | LangGraph、MindRoom、LiteLLM 等暂缓引入 | 每项依赖必须对应实际缺口 |

Nextcloud 服务级集成继续被选定；其依赖版本需在首阶段锁定兼容组合。DSH 当前处于 developer preview，因此固定其作用范围与替换接口，实施时固定版本并先验证。上述决定不等于性能、中文质量或生产可用性已经获得验证。

## 2. 首版技术清单

| 模块 | 固定选型 | 实现边界 |
| --- | --- | --- |
| Web 产品界面 | React + TypeScript | 聊天、项目上下文、任务/成果和执行状态；不把执行器原生 UI 作为唯一产品界面 |
| 产品后端 | TypeScript + NestJS | 模块化单体；权限、Policy、业务对象、资产、模型和执行路由分模块 |
| 默认 Worker | DSH，经独立 Adapter | 通过官方 SDK/运行时通信；不修改 Agent 内核来实现核心业务 |
| 兼容 Worker | Hermes，经独立 Adapter | 优先使用能覆盖交互/确认的官方 JSON-RPC 接口；不只依赖文本型 HTTP 响应 |
| 业务主库 | PostgreSQL | 自有项目、任务、决定、成果目录、权限、Run 和事件 |
| 向量索引 | pgvector | 自有知识服务使用；以源版本、权限和 embedding 版本约束 |
| 队列/定时任务 | pg-boss | 产品任务分发、受控重试与调度；业务副作用另做幂等与对账 |
| 通信 Provider | Nextcloud Talk | OCS API、Bots/Webhooks；账号/消息/会话 ID 均经映射 |
| 原件 StorageProvider | Nextcloud Files / WebDAV | 文件与源文件版本；资产目录保存稳定资产 ID、来源映射和内容位置 |
| CalendarProvider | Nextcloud Calendar / CalDAV | 日历事件与可用时间；以源日历为权威来源 |
| 身份 IdentityProvider | 首版对接 Nextcloud Login Flow v2 与用户身份查询 | 上游认证，产品管理工作区角色和业务权限；不以 Bot Token 识别员工 |
| 模型 ModelProvider | 自有配置/调用适配接口 | 云模型或相容 endpoint；chat、embedding、OCR/转写等用途分别配置与验证 |
| 部署 | Docker Compose | 服务与 Worker 分容器，独立持久卷，开发/试用/正式环境配置隔离 |

补充 React、NestJS 和 pg-boss 的理由是把“自有产品层”落实为可开始实现的栈，并让前后端与 DSH 集成主要采用 TypeScript；Hermes 通过进程接口接入，不要求把 Python 引入业务核心。它们属于本次架构决策，尚无本项目性能对测证据。

首版不单独引入 Redis、图数据库或第二个文件存储服务。关系资产先用 PostgreSQL 的关系表表达。未来更换 StorageProvider 为对象存储时，保持 asset_id 与来源/内容位置分离。

Nextcloud 原生客户端可以作为初期消息与通话入口；完整项目/成果体验以自有 Web 界面为准。原生 iOS/Android 客户端和高度定制音视频交互分阶段实施，不把现成客户端当成已拥有全部自有产品功能。

## 3. 模块与数据职责

| 服务/模块 | 拥有的权威状态 | 通过接口访问 |
| --- | --- | --- |
| PolicyService | pack 版本、适用范围、发布记录与规则快照 | 用户/项目范围和任务限制 |
| Identity/Authorization | 工作区角色、业务授权、上游身份映射 | 上游认证与源系统当前权限 |
| Project/Task/Artifact | 项目、业务待办、决定、成果版本目录、反馈 | 通信记录、文件内容与日历 |
| Asset/Knowledge | 资产目录、关系、派生索引、检索与引用规则 | 源系统内容与当前访问权限 |
| RunService | 运行状态、输入、确认、事件、消耗、回执与幂等记录 | EngineAdapter 和工具服务 |
| EngineAdapter | 引擎会话映射、进程与缓存生命周期 | Run 上下文、获准工具和模型配置 |
| ToolGateway | 工具注册、授权检查、实际操作与回读 | 各 Business Provider |
| 各 Provider | 外部 ID 映射和同步游标 | Nextcloud 或后续替代服务 |

上游消息、原始文件、日历仍以各自来源为准；产品数据库只存映射、必要副本、索引和业务关联。不能把数据库副本和上游对象同时作为可自由修改的两个主记录。业务权限以产品许可与源系统许可的交集为准。

Nextcloud 与自有产品使用独立逻辑数据库/迁移空间。通过公开 API 集成，不直接修改 Nextcloud 表结构。

## 4. Policy Pack 的执行

每个 Run 固定 policy pack 版本与上下文快照。运行中撤权或取消立即重新约束后续工具调用；旧快照不能覆盖当前有效权限。

1. 产品后端根据组织/项目/任务/个人偏好组合规则。
2. 硬规则由业务服务强制检查，例如范围、权限、可用工具、预算与有效授权。
3. 软规则通过提示、界面、通知合并和成果评价实现。
4. 用户的具体反馈保存为 A09；不会自动改写全公司规则。
5. 执行器生成的 Skills/记忆可以形成候选方法资产，组织级发布需由有权维护者确认。

两个执行器接受同一规则和验收，不要求生成逐字相同的回复。原始文档和消息是任务数据，不取得修改 Policy 的权力。

## 5. 统一执行契约

以下是自有产品接口设计，不是 DSH 或 Hermes 的原生协议。

统一操作：
- describeCapabilities：报告执行器/版本支持的动作与事件。
- startRun：启动受控任务。
- sendInput：补充输入或纠正。
- respondToRequest：回答有效的澄清或确认请求。
- cancelRun：请求停止后续执行。
- getRun / subscribeEvents：查询与订阅标准状态和事件。

startRun 最少包含 run_id、workspace_id、已验证 subject_ref、conversation_ref、capability_ids、policy_snapshot_ref、context_asset_refs、model_profile_ref、tool_scope_ref、时间/步骤/费用限制。密钥原文不进入消息、事件或向量索引。

标准事件：run.started、message.delta、progress.updated、input.required、action.proposed、action.completed、artifact.updated、usage.updated、run.completed、run.failed、run.cancelled、run.recovery_required。事件带 event_id、run_id、单次 Run 内 sequence、occurred_at、schema_version 和负载引用；可重连与去重。

标准状态：queued、running、waiting_input、waiting_confirmation、succeeded、failed、cancelled、recovery_required。确认状态归产品拥有；适配器负责双向转换请求 ID、参数和结果。超时、取消、重启后不得复用已失效的确认。动作对象、参数或权限变化时重新校验。

引擎检查点与原始日志可以作为不透明附件保存，企业会话、任务、资产和回执使用产品格式。不把隐藏推理过程设计为跨引擎状态迁移的前提。

兼容能力声明分共同核心与可选扩展。核心业务只依赖两者通过验收的共同能力。某引擎独有能力必须显式声明，不能静默降级为“文本回答”。

## 6. 模型与凭据

ModelProvider 保存 provider、endpoint、model、purpose、credential_ref、使用主体/工作区与额度策略。公司 Key 与个人 Key 有明确优先级和使用范围；允许用途与员工授权由服务端决定。

凭据加密保存在服务端，解密边界与数据库权限分离；执行器只获得本次运行允许的凭据/代理访问。并发任务不得通过修改共享全局模型配置来切换员工 Key。切换引擎时由适配器转换模型配置，并验证该模型在对应引擎中的工具调用能力。

尚未选定具体模型、embedding 模型、OCR/转写供应商和单价；这些属于可配置模型配置及实测项，不影响当前接口和数据所有权。embedding 更新以新索引版本重建并校验，不能混用不同维度/空间。

## 7. 任务可靠性与隔离

产品维护队列、Run 和真实业务结果。Worker 通过租约取得执行权；业务动作以稳定 action_id 和 idempotency_key 记录。任务分发成功不等于外部业务副作用恰好执行一次。

外部接口支持幂等键时透传；不支持时结合外部对象 ID、动作记录和状态回读。执行结果不明时进入 recovery_required 对账，不立即盲目重试。取消阻止后续动作，已经发出的消息或已创建对象需要另行补偿，不能假装撤销。

引擎进程、文件挂载、工具范围、凭据与会话相互隔离。DSH 按任务/执行上下文管理运行目录；Hermes 不允许并发写同一 profile。产品侧共享知识通过服务访问，不通过共享引擎可写目录实现。

Worker 无公司数据库管理员凭据，不直接访问未授权业务系统；企业业务动作统一经过 ToolGateway。涉及本地文件处理的命令在受限工作目录运行。具体容器与网络策略在实施中验收，本次没有声称沙箱已实现。

## 8. 引擎切换的固定语义

- 新任务：按 workspace/用户/任务类型的路由配置选择执行器。
- 已完成会话：从产品可见历史、成果引用和当前状态构建新上下文；不导入旧引擎私有检查点。
- 运行中任务：继续由原执行器完成；如必须转移，先停止并核对副作用，在确认安全的业务边界创建关联的新 Run。
- 企业资料：保持同一资产 ID、知识服务和业务权限，无需因更换执行器迁移企业知识库。
- 回退：调整新任务路由即可；旧任务、模型能力差异和已发生动作按上述规则处理。
- 维护：升级原生协议/模型时仍可能需要修改 Adapter 与测试。目标是业务/前端/资产服务不随引擎切换而改，不承诺零适配成本或原生状态热迁移。

首阶段就为 DSH 与 Hermes 实现最小 Adapter，并运行相同 E01–E10 场景，防止只验证单引擎后再补抽象。

## 9. 资产与知识服务

资产服务独立实现接入、对象选择、解析、版本、关系、索引、检索、来源引用、撤权与删除。默认不全量接入公司数据。

检索先取得服务端校验的作用域，再在允许集合内召回/重排，输出前检查当前访问权限。不能先把全公司命中内容交给模型再请求模型过滤。查询参数中的员工/工作区声明必须由服务端绑定。派生摘要、缓存与组织记忆同样遵守来源可见范围。

pgvector 首版结合 SQL 元数据/精确字段检索；中文关键词分词、召回和重排需要专门样例验证，不假定默认英文全文检索就满足中文场景。结果返回 asset_id、源对象、源版本与可定位引用。

具体公司数据源、文件夹、群组、成员和时间范围仍为空，待配置来源绑定。当前只固定其契约，没有导入数据。

## 10. 固定验收与未验证项

结构一致性检查：Policy/Capability/Asset/Evaluation 编号唯一且互相引用有效；两执行器均有适配定义；实际来源绑定为空。此类检查只验证规格一致性。

实施必须覆盖：
1. DSH 与 Hermes 同一任务经相同权限工具完成实际成果，返回可检查对象。
2. 两个员工并发使用，凭据、会话、确认与资产可见范围不串用。
3. 撤权后，搜索、缓存、派生结果和进行中任务遵守新权限。
4. 重复事件、超时、执行后断网与进程重启可恢复或进入待对账，避免重复业务动作。
5. 引擎切换/回退后，业务、前端与资产契约保持一致；原生会话热迁移不在承诺内。
6. 文件与消息版本、中文检索引用、修改反馈和资产删除全链路正确。
7. Talk 跨端同步、手机通知、认证吊销；会议阶段还要验证 TURN/通话组件。
8. 模型费用与任务耗时实测；DSH 升级、Hermes 协议变更与 Provider 升级有回归记录。

实际生产容量、成功率、延迟、中文质量、模型费用、组件兼容组合和完整依赖许可证清单均未测试。初次实现时生成 runtime-lock 清单，锁定 Node/数据库/Nextcloud/DSH/Hermes/库版本及镜像摘要；不直接跟随 main/master 或 upcoming 文档版本部署。

## 11. 第一阶段不进入核心的组件

- LangGraph / MindRoom：已有执行器与产品任务状态服务，暂不重复引入。
- Nextcloud Assistant / Context Chat / Context Agent / Talk AI Bot：可研究或作为受控工具来源；当前不承担产品执行、模型配置或唯一知识存储。Context Agent 文档还明确当前不支持横向扩展。
- LiteLLM：保留 ModelProvider 边界，出现实际路由需求后再加入；企业功能许可另查。
- Mem0/OpenViking 等：作为未来记忆服务适配候选，不成为企业事实或知识的唯一主记录。
- 独立 Qdrant/Milvus、图数据库：按实际规模或关系查询瓶颈再决定；保留服务接口。
- Flowable：复杂审批阶段再引入；首阶段任务确认由产品 RunService 管理。
- LiveKit：当前沿用 Talk；独立音视频需求成立时再评估。
- 原生全端重写、Kubernetes：不作为首阶段前置条件。
