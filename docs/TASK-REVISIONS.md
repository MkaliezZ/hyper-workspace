# 待办修改与版本契约

映射 P02/P04/P07/P08、C03/C05/C07、A01/A02/A06/A10、E01/E02/E04/E07/E09/E10 子集。固定技术和三层定义不变；这不是完整场景验收。

## 入口与允许动作

项目待办行的“修改”打开同一个编辑器，人工与 AI 均可改标题、负责人文字标记、截止日期和 open/done 状态。日期可明确清空。负责人目前是文字标签，尚未绑定企业员工 UID；标记完成只改变产品记录，不代表独立验收实际工作，也不发送企业通知。

- `GET /api/tasks/:id` 返回当前记录与最近 20 条版本快照。普通项目成员须有当前成员权限，来源关联项目还须通过本人来源权限检查；执行 Run 仍仅对发起人可见。
- `PATCH /api/tasks/:id` 使用严格 `TaskPatch`，前端携带 `expectedVersion`。旧客户端暂可省略该字段；并发保护保证限于携带版本的调用，不能宣称所有旧客户端都具备 CAS。
- `POST /api/runs` 的 `revise_task` 必须绑定 `taskId`、`expectedTaskVersion`、会话、执行器、模型连接、指令和幂等键。服务端限定目标属于当前项目，并复核模型前、实际写入时的版本与权限。
- DSH 和 Hermes 只可提出一项 `task.update`，参数仅为四个可编辑字段。身份、项目、目标和版本由后端持有，模型不能覆盖。演示 fixture 单独标明不调用模型。

模型输入仅含选中待办的当前四字段、ID/版本、引用、当前 UTC 时间、Asia/Shanghai 时区和员工指令，不包含项目讨论或文件正文。来源访问验证仍可能调用源系统。当前时区固定，企业/员工偏好配置尚未实现。未保存草稿不发送给模型；修改指令可能产生模型费用，运行仍受既有输入/时间/输出限制，尚无组织金额配额。

## 版本、回执与人工接管

人工与 AI 共用 `patchProjectTask`：锁定当前待办，在事务内检查当前成员、项目/版本；任务记录、版本快照和 AI 动作保存原子化。无字段变化时返回 `changed:false` 和当前版本，不追加虚假修改记录。AI Run 仍保留自己的动作回执、上下文引用与 `task.updated` 事件；模型原始回复不公开为项目消息。

新建待办由共享服务记录 v1；修改递增版本并保留操作者、来源 Run、设备凭据引用及 Policy 版本。业务接口不提供历史更新操作；这不等同于数据库管理员不可篡改的审计存储。

AI 运行期间允许人工接管。人工先保存会使旧 AI 结果冲突失败，不覆盖新值。AI 完成后只刷新当前版本提示/历史，不覆盖编辑框的人工草稿；员工显式“读取当前版本”后才替换。人工保存期间锁定字段，并先采用服务器返回的已保存记录。关闭或切换项目后，迟到的保存/发起响应不能恢复旧编辑器或旧项目。

执行检查发现取消/撤权时阻止新的任务修改；已提交动作不会因为取消而回滚。源系统权限与本地数据库没有跨系统原子性，存在检查后的在途窗口，边界同 [来源项目契约](PROJECT-SOURCE-SCOPE.md)。复用幂等键返回本人已有 Run，不重复执行写入。版本冲突需重新读取并按新版本发起，不能自动无条件重试旧修改。

## 迁移、生命周期与回退

迁移 `016_task_versions.sql` 加入任务版本、`cw_task_versions` 和 Run 目标/版本约束。旧任务只记录迁移时当前状态，标为 `legacy_snapshot`，原修改人未知；记录时间是捕获时间，不伪造旧操作时间。开发 seed 等直接插入缺少历史的任务，在第一次业务修改前以同样标记捕获旧状态。

升级前备份并停止旧 API/Worker，运行迁移后一起启动同版本代码；不可用旧 Worker 处理新工作类型。快照随任务删除级联，已引用任务的 Run 外键阻止直接删任务，当前产品没有待办删除接口；不是永久脱离任务保留的归档系统。

发现问题先停用新任务修改入口/Worker并保留数据库与失败回执。回退代码必须禁止新 `revise_task` 派发并对账已有 Run；不自动删新列/历史。若确需恢复旧数据库，只能在隔离验证过的备份上恢复并确认升级后的新增业务记录如何处理，避免无声丢失。
