# 待办检查与静默差异

对应 P03/P04/P07/P08、C02/C03/C05、A02/A06/A10、E03/E04/E09/E10 的子集。固定三层和技术栈不变；组织级通知偏好、金额预算与完整 E03 尚未验收，原冻结快照保持不变。新增有限次数的 [定时跟进](FOLLOW-UP-SCHEDULES.md) 使用相同检查服务，其范围与证据另行记录。

## 员工流程

在获准的项目中选择“发起任务 → 检查待办进展”，填写要求并选择模型/执行器。DSH 默认，Hermes 共用相同业务服务；演示执行明确标记 fixture。界面说明这是一次检查，不会创建定时任务。

静默只表示不重复发项目消息。当前每次主动检查仍经过所选原生执行器和模型，可能产生调用费用；本项未实现按变化预筛选的免调用调度或预算策略，不宣称无变化时没有模型消耗。

首次检查建立项目共用基线，并在执行状态栏返回当前待处理数量；不向讨论区发消息。后续状态相同仍保留 Run 和检查回执，在状态栏说明“无变化，本次未发消息”。待办发生变化时，产品核心将本次可见差异合并为一条项目消息；随后再次检查相同状态不重发。

当前比较事项、负责人、完成状态、截止日期及对象的新增/移出。人工待办界面和获准的 AI 待办动作都写入相同产品表，检查从该表回读。它比较两次观察的状态，不是每次编辑的完整事件审计，不根据仅有时间流逝推断逾期或紧急程度，也不自动催人。所有纳入比较的字段变化都记录，不声称已经实现重要程度评分或个人通知偏好。

## 契约与权限

| 项目 | 规则 |
| --- | --- |
| 入口 | 既有 POST `/api/runs`，`workflow=follow_up`；员工、工作区、项目与设备由服务端验证 |
| 模型输入 | 仅当前项目名称和产品待办的 ID、事项、负责人、状态、截止日期；不加载讨论正文、企业源消息、文件或其他项目 |
| 引用 | `task:<ID>@<字段摘要>` 记录派发时看到的版本；动作时再回读，回执的 `stateDigest/observedAt` 是实际比较依据 |
| 允许动作 | 恰好一次 `follow_up.check {}`；模型不得选择项目、员工、收件人、基线或通知判断 |
| 结果 | 回执含 `reason/notify/pending/changes/baselineRunId/observedAt/stateDigest/notificationMessageId/summary`；差异含对象 ID、前后字段与变更类型 |
| 通知 | 仅向当前产品项目讨论写一条事实消息；前十项差异进入消息，完整差异保留在 Run/动作回执。没有 Talk 投递、手机推送或邮件 |
| 范围 | 每个工作区/项目一份共享基线，避免两个员工或执行器对同一状态重复通知；不跨项目合并 |
| 上限 | 最多 1000 项待办；超出则明确失败且不移动基线。仍遵守既有 100000 UTF-8 字节输入、执行时间和模型输出上限 |

模型文本不决定业务状态或最终跟进总结。无变化时不把生成文本写入项目；有变化时消息和总结均由权威字段生成。模型不能伪造“已通知外部”或“全部完成”的产品回执。原生引擎工具继续禁用，两个执行器通过同一 EngineAdapter/ToolGateway 进入 `FollowUpService`。

工作区成员、设备与来源项目成员权限沿用现有服务：发起、载入、模型派发前、每个动作前和最终提交重新检查；真实来源运行中定时核验。普通项目成员可看到项目内变化消息，Run/events 仍只对发起人开放。基线中的上次 Run ID 只是关联，不授予读取另一员工 Run 的权限。撤权不允许通过历史基线恢复访问；已复制内容和已读消息无法撤回，跨系统权限检查仍有在途窗口。

## 原子性、失败与恢复

`cw_follow_up_baselines` 由产品拥有，保存当前任务快照、上次 Run 和检查时间。迁移 012 使用已有项目/工作区复合外键约束，并为按工作区/项目/ID 读取待办建立索引。

动作事务先验证运行租约与成员，再对当前项目行取得短事务锁，串行读取/比较/更新基线。模型和来源 HTTP 调用在该事务外，当前任务一次 SQL 读取。并发检查无论来自哪个执行器，都基于前一份已提交状态比较；首个检查合并消息，后一个相同观察保持静默。检查过程中又有编辑时，后续检查会发现新的当前状态，不承诺重现两次检查之间已恢复原值的短暂变化。

基线、变化消息和 `cw_actions` 完成回执在同一数据库事务提交。保存回执失败时三者全部回滚，下一次仍能报告该变化；业务动作提交后发生中断则进入 `recovery_required`，已经写入的消息与回执保留，不假装撤销。重复处理同一 Run/动作沿用既有租约与幂等记录，不重复发消息，也不把检查自动恢复为新模型调用。

排队取消、工具越范围、重复动作、模型失败、派发前/动作前失权或数据过大均不能移动基线。基线仅保存一份当前任务状态，旧事实仍可能保留在消息/动作审计中；统一保留、清理和成员停权数据治理尚待补齐。普通项目运行目录继续沿用既有策略，不能把本项当作已经完成生产磁盘清理。

## 迁移与回退

升级前备份并停止新执行，应用 `012_follow_up_baselines.sql` 后共同部署 API/Web/Worker，再运行部署初始化以给运行角色授予新业务表的 DML 权限。管理员仍只用于迁移/初始化。既有任务、成果、模型配置和历史 Run 不改写；本地开发库已明确核对为 localhost 的 `hyper` 后迁移。

回退前停用跟进入口并停止相关执行，先核对已提交的消息与动作。保留基线和回执，不删除记录来强制重新通知；旧 Worker 会恢复旧的非静默行为，不能和新版本混用执行同一跟进队列。优先向前修复，正式回退演练尚未完成。
