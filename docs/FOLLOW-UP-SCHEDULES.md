# 有限次数的定时跟进

对应 P03/P04/P07/P08、C01/C03/C05/C07、A01/A02/A06/A10、E03/E04/E09/E10 的子集。沿用 [待办状态比较](FOLLOW-UP.md)、默认 DSH、兼容 Hermes、产品拥有调度与资产的固定基线。未完成组织级通知偏好、金额预算、重要程度评分、真实供应商质量或完整 E03/E01–E10 验收。

## 员工流程

在项目“任务 → 我的定时跟进”中指定间隔、最多检查次数、执行器与 chat 模型连接。可以直接保存，也可以选择“让 AI 设置”；创建、暂停、恢复、取消都进入同一配置服务。AI 只提出 `follow_up.configure {}`，服务端执行员工已经选定的操作、目标版本和限额，模型不能改写它们。

保存后尽快执行首次检查。每个工作区/员工/项目只允许一个活动或暂停的跟进；旧记录保留。间隔 15–1440 分钟，总发起次数 1–96，最晚创建后 30 天停止。创建时固定实际模型配置 ID，后续不会因默认连接改变而换 Key；恢复会重新核验原模型，并显式绑定当前登录设备。

每次仍是独立 `follow_up` Run，使用原生执行器与所选模型，再由产品比较权威待办。首次及无变化不发项目消息，有变化合并一条消息；不自动投递 Talk、邮件或手机推送。UI 显示“已发起 X/Y 次”，达到次数上限表示不再调度，最后一次检查仍可能排队/运行或失败，可以打开最近 Run 核对。

次数约束的是检查 Run 的发起数量，不是成功次数、模型 HTTP 请求数或金额。AI 配置本身也是单独的 Run，不包含在检查次数里；原生运行时可能重试模型请求。当前没有金额封顶、公司总额度或无变化免模型调用的承诺。

## 服务与资产契约

| 项目 | 规则 |
| --- | --- |
| 人工入口 | GET/POST `/api/conversations/:id/follow-ups`；仅当前主体自己的配置；列表最多最近 20 条 |
| 配置请求 | `{plan,engine,modelProfileId?,idempotencyKey}`；create 的 plan 固定 `intervalMinutes/maxChecks`；pause/resume/cancel 固定 `scheduleId/expectedVersion` |
| AI 入口 | POST `/api/runs`，`workflow=configure_follow_up`，同一 `followUpPlan`；模型只能提出一次空参数 `follow_up.configure` |
| 模型上下文 | 仅服务端固定的计划、项目/会话引用和模型配置 ID；不加载企业消息、文件、其他项目、Key 或源凭据 |
| 结果 | 配置回执含稳定 schedule ID、状态、版本、执行器、模型引用、间隔、次数、下次/到期时间和最近 Run；人工与 AI 均保存幂等回执 |
| 持久化 | `cw_follow_up_schedules` 保存主体、项目/会话、设备引用、限额、代际版本、租约与派发进度；`cw_follow_up_configuration_receipts` 保存配置回执；Run 保存计划或调度绑定 |
| 调度 | 独立 Worker 每次恢复扫描时发起受控派发；数据库领取到期记录，pg-boss 分发实际 Run；执行器 cron 不参与 |
| 权威性 | 原生引擎、模型或本地记忆都不能拥有唯一调度记录；检查结果继续进入产品基线、动作和消息服务 |

配置记录不进入向量库。取消不删除历史配置/Run/动作/已发项目消息；统一保留和清理策略仍待完善。所有 ID、角色、工作区和设备引用由后端绑定，配置请求不接受这些身份声明或任意收件人。

## 权限、取消与预算边界

创建和恢复核验当前项目、源成员资格、设备、模型用途/可见范围及引擎能力。派发从保存的主体/设备构建 Subject，再查当前产品角色、来源和同一模型；不把其他设备密码或新默认连接用作兜底。停止操作按工作区/主体/目标会话核对归属，其他成员和管理员身份不能替另一个员工使用个人 Key。直接暂停/取消不要求模型可用，也不要求仍能读取已撤权的来源项目；仍需有效产品登录。

每次配置使用预期版本。暂停、取消或恢复都增加代际版本，并停止旧代尚未完成的 Run；发起、动作前及动作事务内检查当前代际、最近 Run、到期时间和当前授权。锁顺序保持目标 schedule → Run/成员 → 项目，远程来源/模型核验不放在数据库事务内。暂停返回后不会开始新的业务动作，已提交结果保留；不是回滚或瞬时撤回已发送给模型的输入。

失败、取消或待对账的上次检查会暂停未来调度，避免反复花费。AI 配置只有在创建/恢复它的 Run 成功后才允许派发；配置动作已提交而 Run 进入待对账时，记录保留但先暂停，须员工核对并明确恢复。恢复不会重置已用次数、延长 30 天到期时间或复活旧 Run。

## 重启、并发与失败

到期领取使用短事务租约和 `FOR UPDATE SKIP LOCKED`，每批最多 4 条，并行核验；单 Worker 的派发扫描不重入，多 Worker 由数据库仲裁。租约 90 秒，过期可重新领取。确认租约、代际、活动状态和当前成员后，在同一事务创建一条 Run、增加已发起次数、保存最近 Run 和下次时间；队列发送失败仍能由既有 queued Run 恢复扫描补发。

同一代的上次 Run 未成功时不重叠派发。停机错过多个周期只发起当前一轮，下次从当前时间加间隔计算，不补跑一串错过的检查。模型或来源在派发核验时不可用会暂停并显示固定错误说明，不记录上游原始报文/凭据。失败后需明确恢复；当前没有自动指数退避、通知偏好或失败推送。

队列恢复、过期运行对账与 Worker 健康探针先继续工作，来源核验异步进行；上游响应慢不会阻止这些扫描。健康探针仍只证明数据库探测及时，不代表公司来源或模型可用。

## 迁移、升级与回退

`013_follow_up_schedules.sql` 新增调度、配置回执和 Run 绑定，约束有限次数、活动状态/下次时间、演示/原生模型绑定，以及计划/工作流、调度/代际的一致性。项目/工作区复合外键沿用既有约束。旧 Run、任务、成果和模型不改写。

升级前备份并停止新任务与旧 Worker，先由管理员迁移，再运行部署初始化授予新业务表的运行角色 DML，最后共同升级 API/Web/Worker。旧 Worker 没有代际取消和 AI 配置语义，不能混跑。原生 Worker 不持有数据库管理员凭据。本地已核对并仅迁移 localhost 的 `hyper`/隔离 `hyper_test`；发布前收紧未发布迁移的空值约束时，两处开发数据库同步约束，未清空数据。

回退前暂停/取消活动跟进并停止派发，核对最近 Run/已提交动作，保留所有配置与回执。不要删除行、重置计数或去掉调度绑定来触发重跑；优先向前修复。正式回退、备份恢复与公司环境演练尚未完成。
