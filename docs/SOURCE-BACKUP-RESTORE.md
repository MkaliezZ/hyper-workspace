## 已完成的独立恢复

恢复使用同一固定版本镜像：Nextcloud **33.0.10**、Talk **23.0.12**、PostgreSQL **17**。在新文件卷和新的 PostgreSQL 容器中解包、导入；新数据库、角色及随机凭据独立创建。只在恢复副本中替换数据库目标、受信主机和规范 URL，原备份不变，原服务连接不变。

恢复网络由 Docker internal 网络隔离，不发布端口。副本的 OCC 状态回读为已安装、无需升级，Talk 启用版本正确；在副本执行 data-fingerprint 后解除其维护模式，再通过独立受限检查容器读取：

- 恢复来源返回已安装、非维护状态，版本 33.0.10。
- 合成管理员从真实 WebDAV 读到已备份的 Markdown 原件，内容包含“北侧”和 `HW-CLOUD-042`。
- 另一合成员工访问该管理员原件被拒绝，未把恢复当作共享或授权扩大。
- 未替换原库、未修改原来源绑定，也未把产品切到恢复副本。
- 检查后移除本次临时容器、恢复卷和隔离网络；原 API、Worker、来源、产品数据库和向量服务保持健康。

首次恢复测试因检查容器未连接标准输入而遇到 EPIPE；修正后，受限探针因原账号文件的所有权遇到 EACCES。保留这两次失败，复用已校验归档，只在隔离资源复验。最终使用管理员受限的两名合成账号副本供探针读取，未放宽原文件权限或向外暴露凭据。以上不记为首轮通过，也没有重复停原服务。

## 公司部署时的执行顺序

1. 为正式工作区生成独立配置和主密钥；维护窗口内阻止新业务，等待或明确处置现有 Run。确认目标为指定公司机器，检查既有容器/卷及备份路径，保留原配置。
2. 对自有 API/Worker 和来源应用做上述停写处理，取得产品库、来源库、来源文件卷的同一维护窗口快照；保留版本、镜像摘要、清单、校验值及恢复所需私有配置。任何捕获失败都应恢复原服务并将不完整目录隔离。
3. 用新数据库、新卷和隔离网络做恢复检查，验证原件、来源账号权限、产品资产/密文/回执、旧队列和未完成 Run 的隔离；不把原产品指向该副本来“试一下”。
4. 验证业务读取和恢复状态，再另行安排实际切流与回退。公司机器、实际 IP/证书信任、用户数据和离机保管仍在公司环境中核对。
